# 规范食谱整理

把来源内容转换为可直接下厨使用的食谱。忠实保留已知信息，不以常识补齐来源没有提供的用量、火候、时间、温度或配比。

开始整理前，完整阅读 [references/recipe-format.md](references/recipe-format.md)。

## 工作流程

### 1. 确认交付方式

先确认用户只需要在对话中查看食谱，还是需要保存为 Obsidian 文件。只在对话中输出时，不询问仓库路径。

需要保存文件时，在任何写入前确认：

- Obsidian 仓库的绝对路径
- 仓库内的目标目录
- 是否允许创建不存在的目标目录
- 是否允许只读检查目标目录、模板、附件设置和必要的 `.obsidian` 配置
- 同名或高度相似食谱出现时的处理方式
- 是否保存原始材料；默认只在 YAML 保存标题和来源链接，不复制原始总结
- 存在图片或附件时的存放规则

根据规范化后的菜名自动生成文件名，除非用户指定其他名称。不要把文件名作为固定问题重复询问；只有标题不明确、存在冲突或用户要求自定义时才询问。

把环境、路径、写入范围和冲突处理合并后一次确认。获得写入授权并排除同名冲突后，直接生成一份尽可能完整的 Markdown 初稿；不要先围绕配方缺失、疑似错字或一般不确定项反复询问，导致用户没有成稿可供判断。

### 2. 检查仓库与相似食谱

用户允许检查后：

1. 确认仓库和目标目录是否存在。
2. 只检查目标目录、模板、附件设置和必要配置，不读取无关笔记。
3. 在目标食谱范围内搜索规范菜名、常见别名、核心关键词和主要食材组合。
4. 对搜索得到的少量高相关候选进行内容核对。
5. 发现同名或高度相似食谱时停止写入，询问用户是更新、合并、作为变化版本还是另建笔记。

禁止只凭文件名判断是否重复，也禁止在没有确认时覆盖、合并或新建近似重复食谱。

### 3. 先出稿，再讨论关键缺失

获得写入授权后，先按来源完成整理并写入初稿，再把文件交给用户查看，同时简要说明：

- 对来源做了哪些高置信度语义纠正；
- 仍然存在的关键主料、核心配比或炸制、烘烤、发酵条件缺失；
- 相互冲突且无法可靠取舍的用量、时间、温度或步骤；
- 来源中突然出现但缺少方法的非显然前置处理；
- 哪些信息来自作者，哪些来自评论区实测或其他补充来源。

交付时把缺失与未知项从其他说明中独立出来，使用醒目的 `待确认 / 待补充` 小节：

- 每个待确认项单独一条，优先列出主料重量、核心配比、关键时间、温度和非显然预处理；
- 写清楚缺少的具体信息，尽量提示用户可在视频的配方卡、字幕或对应步骤中查找；
- 不把已完成内容、格式说明和一般总结混入该小节；
- 没有待确认项时明确写 `待确认 / 待补充：无`；
- 用户补充后直接更新初稿，不重复解释已经确认的项目。

只有以下情况可以在初稿前暂停：

- 目标路径、写入范围或覆盖授权尚未明确；
- 存在同名或高度相似食谱，需要用户决定更新、合并或另建；
- 缺失或冲突会决定输出一份还是多份食谱，或会实质改变主要流程；
- 多种解释都合理，且不同解释会改变核心食材、过敏原、用量或安全条件。

用户查看初稿后再讨论和迭代。普通模糊量保持原样；真正影响复现的缺失写入“整理提示”，不要因它们存在而阻止初稿落库。

### 4. 识别可执行内容

提取：

- 菜名和原内容标题
- 原始内容来源链接
- 食材及全篇总用量
- 必要设备
- 前置预处理
- 按执行顺序排列的制作步骤
- 来源明确提供的火候、时间、温度和完成状态
- 会改变食材或主要流程的可选变化
- 影响复现的关键缺失或冲突

默认删除：

- 作者故事、地域介绍和文化背景
- “灵魂原料”等修辞性评价
- 成本、效率和不同做法的宣传性比较
- 推荐场景、情绪描述和重复内容
- 未经可靠计算的营养、减脂或健康判断
- 不影响操作的一般科学原理

若原理可以转化为操作要求，只保留操作要求。例如，把“热糯米会融化冰沙”合并到冷却步骤，不单独保留原理章节。

区分“材料载体链接”和“原始内容来源”：

- 用户提交的总结页、转存页、聚合页或分享笔记只是材料载体，不写入 YAML `来源`；
- 检查载体页中明确指向的视频、图文教程、文章或原帖链接，把这些原始内容链接写入 `来源`；
- 存在多个真正参与食谱整理的原始来源时全部记录；
- 原始链接能够确定时，`原内容标题` 使用原始内容的标题，不使用自动总结生成的标题；
- 载体页没有提供或无法解析原始链接时，才把载体链接作为兜底来源，并在交付时说明。

### 5. 区分主配方与变化

- 把口味替换或少量材料替换放入“可选变化”。
- 把使用不同材料体系但仍是同一成品的简化方案作为独立变化，单列食材表，禁止与主配方总量合并。
- 当两个方案的主要流程、成品或用途明显不同，输出为两份食谱。
- 不保留纯宣传性的“正宗版、懒人版”比较，只保留实际配方和操作差异。

### 6. 核对事实边界

逐项标记来源表达：

- 明确数值：原样保留并统一单位书写。
- 明确范围：保留范围。
- “适量、少许、按口味”：原样保留，不报告为缺失。
- 来源未提供：写“未说明”，不得改写为“适量”。
- 来源或总结明确标注的估算：用量保留原始表达，把估算放入备注。
- 前后冲突：不擅自选择，将冲突放入开头的“整理提示”。

禁止根据容器、画面、常识或其他食谱自行换算“一勺、一碗、一把”等非标准量。仅在来源明确给出换算关系时同时记录。

允许纠正上下文能够唯一确定的明显 OCR、字幕或转写错误。纠正必须同时满足：

- 原词与菜谱语境明显冲突；
- 全文存在一个高度明确、能使食材与步骤闭合的替代词；
- 纠正不涉及臆造数值、比例、温度或额外步骤。

直接把纠正后的词写入初稿，并在交付时告知用户。例如炸鸡面糊中的“果粉”，若全文明确存在炸鸡裹粉且没有任何水果粉用途，可规范为“裹粉”。若仍有两个以上合理解释，保留来源表达并在成稿后讨论。

### 7. 建立食材总表

主配方建立一张全篇食材总表，展示开始制作前需要备齐的全部食材。阶段内可以为提高可读性重复展示该阶段用料，但不得用多个阶段表取代总表，也不得把阶段用量误算为额外用量。

按烹饪角色而不是来源出现顺序排列食材：

1. 决定菜品主体的主料，例如肉类、鱼类、豆制品、主食和主要蔬果；
2. 直接构成成品的重要辅料，例如鸡蛋、奶制品和配菜；
3. 面粉、淀粉及其他结构性材料；
4. 香辛料、调味料、腌料和酒类；
5. 食用油及其他烹饪介质。

同一层级内再按实际使用顺序排列。普通清洗水、焯水、煮制用水、快速蘸水和“少许水调状态”等不进入食材总表；只有水具有明确用量或比例，并直接决定面团、面糊、汤汁、卤水、饮品等成品结构时才列为食材。

- 在“食材”列写名称。
- 在“用量”列只写数量、范围、“适量”、“少许”或“未说明”。
- 在“备注”列只写影响用量理解或选择的信息，例如“可选”、“分次使用”、“总结估算约 200 g”、“可用白粽子替代”。
- 不在备注中写食材用途。
- 不在备注中写切块、切丝、冷却、浸泡等处理动作。
- 同一食材分阶段使用时，在总表写总量；在对应准备或制作步骤写各阶段用量。
- 只知道总量、不知道分配量时，备注“分次使用”，不得自行分配。
- 同一食材在一个阶段有明确量、另一阶段用量未说明时，用量写“至少 + 已知量”，备注说明哪个阶段的用量未说明；不要在用量列拼写“已知量 + 未说明”。

所有 Markdown 食材表遵守同一表格契约：

- 固定使用 `食材 | 用量 | 备注` 三列，每个数据行都必须写满三个单元格；
- 备注没有内容时写 `&nbsp;`，使 Obsidian 视觉上保持空白，同时避免末尾空单元格被渲染器折叠；
- 表头、分隔行和每个数据行的列数必须一致；
- 不按行省略备注列，不使用合并单元格，也不因某行没有备注而改变表结构。

阶段用料较多时，不要把大量名称和用量塞进一个长句：

- 默认5项及以上，或行内表达已经明显难读时，在对应三级标题下增加同样的三列表格；
- 1–4项且关系简单时，继续使用自然语言；
- 阶段表只重复该阶段实际使用的已知用量，随后用简短步骤说明操作；
- 总表仍保留全篇总量，阶段表不改变总量规则。

默认使用普通食材名称，不主动创建 `[[食材]]` 双链。只有用户提供现有食材笔记、明确要求建立链接，或当前名称已经以双链形式出现时才保留或添加。

用户明确要求建立或维护食材、技法笔记时：

- 先检查目标仓库中是否已有同名笔记或既定目录，避免重复创建；
- 在食谱的食材表或最自然的首次出现处添加双链；需要指向具体方法时可以链接到对应标题；
- 配套笔记不仅记录可执行做法，还要记录来源明确提及、且有助于理解操作的原理；
- 把来源解释写成“来源称”或“该方法认为”，不要把未经核实的机理提升为普遍科学定论；
- 把剂量、时间、适用条件、风险和失败表现与原理分开，来源未说明的部分继续标为“未说明”；
- 食谱正文仍以直接下厨为目标，详细原理留在配套食材或技法笔记中，避免重复膨胀。

用户要求关联可复用做法知识时，统一使用“技法与味型”，不再把烹饪技法、调味结构或二者结合的做法模型拆成不同体系：

- 在食谱 Properties 中使用 `技法与味型` 列表，并以 Obsidian 双链关联，例如 `[[水油焖]]`、`[[宫保]]`；
- 配套笔记默认放入仓库既定的 `技法与味型` 目录；没有既定目录时，在食谱目录下创建 `技法与味型`；
- 每篇配套笔记唯一固定要求是包含 `## 关联食谱`，其余章节根据该做法实际拥有的配比、流程、原理、适用范围、风险或变化自由组织；
- 食谱仍保留独立完成制作所需的关键信息，不把配套笔记变成执行食谱的必要前置阅读；
- 同一来源包含多道菜时，只有存在可迁移的共同做法才建立“技法与味型”笔记；不要仅为保存同源关系建立合集页；
- “减脂餐”“快手菜”等仅用于聚合检索的宽泛主题优先使用 Obsidian `tags`，不默认建立专题页；只有用户明确需要策划、菜单或说明内容时才建立专题笔记。

### 8. 补齐前置预处理结构

检查制作步骤中使用的食材状态是否已经形成：

- 对切末、切片、切块、打散等明确且无实质分歧的基础动作，补入“准备”。
- 对泡发、焯水、腌制、发酵、解冻到特定状态等可能影响结果的动作，仅保留来源明确内容。
- 若步骤突然使用“泡发后的木耳”“腌好的鸡肉”等状态，而来源没有提供方法，把缺失放入“整理提示”，不要自行编造。

把开始正式烹饪前应完成的洗切、浸泡、腌制、解冻、调汁、预热、冷冻和冷却放入“前置预处理”。不要把烹饪过程中才发生的动作机械前移。

存在两个以上清晰的预处理阶段时，在 `## 前置预处理` 下使用动作型三级标题组织内容，例如 `### 腌鸡肉`、`### 调干粉`、`### 调面糊`。标题只概括来源已有流程，不得为了结构完整而新增动作。

### 9. 重写制作步骤

按实际执行顺序重组零散描述。每个实质步骤尽量形成完整逻辑：

> 用什么、使用多少、怎么操作、操作到什么状态。

同时遵守：

- 在步骤中重复该阶段实际使用的已知用量，不要求读者返回食材表自行推算。
- 若使用食材全部总量，可写明“全部”或直接写出总量。
- 把来源提供的设备、火候、温度和时间放入对应动作。
- 把颜色、质地、声音、气味等完成判断放入对应步骤，不单设“成功标准”。
- 把失败风险和关键提醒放入对应步骤，不单设“关键提醒”。
- 来源没有说明火候、时间或完成状态时直接省略；只有缺失会严重影响复现时才写入“整理提示”。
- 不为了句式完整而编造信息，也不强迫装盘、盛出等简单动作包含全部要素。

制作包含多个明确工序时，在 `## 制作步骤` 下使用动作型三级标题，例如 `### 裹粉起鳞`、`### 炸制`。按烹饪逻辑重排来源中的零散信息，使每个工序内部可连续执行；不得把合理排序扩张为来源不存在的做法。

### 10. 生成配方指数与综合制作时间

新建食谱时，根据整份成稿生成 `配方指数` 和 `综合制作时间`。完整评分与估时规则见 [references/recipe-format.md](references/recipe-format.md) 的“配方指数”和“综合制作时间”章节。

- `配方指数` 为1–5之间的数值，只使用0.5分档；综合评价食材与配比、流程闭环、关键控制与安全、证据与一致性，并允许有助于操作的原理、状态判断和失败排查小幅加分。
- 大量“未说明”、核心配方卡缺失、关键时间温度缺失、重大冲突或安全条件不明时应用评分上限；科普内容不能抵消核心缺失。
- `综合制作时间` 估算从开始处理食材到可以食用的关键路径，包括主动操作和腌制、浸泡、发酵、冷却等等待；并行步骤不重复相加。
- 来源时间缺失时可以按步骤复杂度估算主动操作时间，但使用“约”或范围；未知的关键等待时间不得自行补造。

编辑已有食谱时不要每次都重新评分：

- 普通增补、单次修订、错字、排版和链接调整保留原评分；
- 用户明确表示“改完了”“定稿了”时，询问是否重新评估；
- 同一食谱在当前协作过程中累计3次实质性修改后，在本轮修改完成时询问一次是否重新评估；
- 用户确认后重新阅读整份食谱，同时更新 `配方指数` 和 `综合制作时间`；
- 用户直接要求重新评分或更新指数时立即执行，不再二次确认。

### 11. 控制 Obsidian 结构

仅输出 [references/recipe-format.md](references/recipe-format.md) 规定的模块。

- Properties 默认只使用 `状态`、`配方指数`、`综合制作时间`、`原内容标题` 和 `来源`；存在明确关联时允许增加 `技法与味型`，宽泛检索主题允许使用 Obsidian `tags`；没有内容时省略对应项。
- 不添加 `类型`、份量、耗时、主动操作、主食材或烹饪方式等未获准属性。
- 只有关键缺失或冲突存在时才添加 `[!warning] 整理提示`。
- 只有存在不可轻易替代的设备时才添加 `[!info] 所需设备`。
- 不记录刀、砧板、碗、筷子、勺子、普通锅铲等常规用具。
- 没有内容的条件模块直接省略，不输出空标题。
- 不在正文末尾重复“来源”模块。
- 不添加总结报告、删除说明或整理过程，除非用户明确要求。

## 输出前检查

确认：

1. 没有把低置信度推测写成事实；高置信度语义纠正已在交付时说明。
2. “适量”和“未说明”没有混用。
3. 食材表是主配方全篇总量，而非阶段分表。
4. 备注没有重复食材用途或处理方法。
5. 步骤使用的加工状态已有准备或缺失提示。
6. 已知阶段用量已写进对应步骤。
7. 火候、时间和完成状态仅来自来源。
8. 提醒与状态判断已合并进相关步骤。
